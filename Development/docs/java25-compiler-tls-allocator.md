# Compiler TLS allocation fallback

A console trace now identifies an actual abort in the SDK's compiler-rt emulated TLS allocator. The linked executable's in-image anchor establishes the load adjustment. Subtracting it from the recorded abort caller and preceding malloc return points to `__emutls_get_address`, specifically the initial per-thread address-array allocation. The completed native call requested 128 bytes and returned null; the disassembly branches directly to abort on that result. This establishes that failure path, not a process-wide RAM limit or a Java heap exhaustion diagnosis.

The JNI packager extracts only `emutls.o` from its temporary SDK libc archive and rewrites its malloc/realloc/free references to the dedicated adapter in `java25/probe/emutls_alloc.*`. The SDK cache and other archive members are unchanged. The adapter uses an aligned size/backend prefix, tries libc first, and then uses page-rounded OS RW mappings. All three allocator references are redirected together so normal releases, array growth and compiler-rt's destructor use matching storage. Failed growth preserves the original data and ownership. Both allocation backends can still fail; compiler-rt retains its existing fatal behavior in that case. There is no heap-size increase or verification bypass.

The adapter and its logger use no compiler TLS or lazy initialization guard. In the initial allocator-only revision, native key setter return/readback failures received a separate `EMUTLS: native key update refused` marker, with the actual result and native identity. That diagnostic preserved the native setter's return value and existing SDK semantics. That initial allocator-only revision did not repair a refused native key update. The subsequent capture and canonical-storage repair below address that separate issue; the HotSpot current-pointer fallback is a different key.

The implementation is scoped to embedded JNI probe packages. This does not change independently loaded shared modules' compiler runtimes. The SDK's aligned variable layout, initialization templates and index assignment remain in the original object. Key ownership and lifecycle integration are described below.

Validation covers the actual adapter header with forced libc and mapping failure under ASan/UBSan, the exact failed 128-byte size, payload alignment, growth/copy and failure preservation, overflow, errno, 1600 concurrent allocation lifetimes and complete release. Target LLVM IR has no emulated TLS or lazy guard. Packaging checks all scoped references and includes the adapter definitions; target console execution is still required.

For the underlying algorithm, see [LLVM compiler-rt emutls.c](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.8/compiler-rt/lib/builtins/emutls.c). The SDK object is adapted in place rather than replaced with that source version.

## Canonical key storage after the next console capture

Build 027 confirms that mappings succeed, but the emutls key setter returns ENOMEM. The same thread repeatedly loses its array: the trace records 247 refused updates and 495 mapped allocations before another compiler-rt abort. Its separate class-loading file now contains records, confirming the consumer FILE-routing repair. The raw logs remain local.

The scoped adapter now also rebinds compiler-rt's key-create/get/set references. A static 1024-identity registry holds the canonical array even when the native setter refuses it or falsely reports success. Lookups retain that array rather than repeatedly allocating it. The native key is still created and updated, and its real failure is logged. A successful canonical store is a logical success for this private compiler-TLS backend. Key creation failure still propagates to compiler-rt. No other platform key is redirected.

The native destructor wrapper ignores its argument, because a refused update after array growth can leave that argument pointing to freed old storage. It instead takes the canonical current-thread array and delegates once to the SDK's original destructor. Explicit null stores also hide stale native values. If native registration failed entirely, there can be no key destructor callback. Therefore linked pthread_create/join calls have narrow lifecycle adapters: a successful join reclaims the remaining array only after native thread destruction; a successfully created thread reusing a native identity reclaims that identity's retired array before the new start routine begins. Monotonic generations prevent an old join from reclaiming a newly reused identity's state.

There is deliberately no reclamation when a start routine returns: that would run before C++ and pthread key destructors, which may still access compiler TLS. A detached or unjoined thread whose native registration failed retains its array until native identity reuse or process exit. This is a bounded registry of 1024 distinct identities per process; exhaustion terminates explicitly rather than aliasing thread state. There are 128 static in-flight start contexts; exhaustion returns EAGAIN before native thread creation. Allocation and destruction never execute under the registry lock. This covers threads created through the linked application runtime; foreign/shared-module thread entry must establish its own lifecycle integration before relying on refused-key fallback and identity reuse.

Retired arrays use the SDK object's two-word header/aligned-variable ABI for matching release. The packager verifies the original SDK 0.42 emutls.o SHA-256 `f12a423ab50bab567caab55986904949f3b15074d253e95b151374054b57d94d` before applying this adaptation, and checks every rewritten reference. It never modifies the SDK cache. The native destructor's original algorithm remains in that object.

ASan/UBSan tests compile the actual adapter with real pthreads, refused and false-success setters, stale native array pointers, repeated lookups, 800 concurrent thread lifetimes, real native destructor ordering, failed create/join, generation reuse and exhaustion, and complete mapped cleanup. A destructor that runs after the start routine returns still reads its expected canonical state. Target IR checks retain the no-compiler-TLS/no-lazy-guard property. Console validation is still pending.
