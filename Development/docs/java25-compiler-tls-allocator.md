# Compiler TLS allocation fallback

A console trace now identifies an actual abort in the SDK's compiler-rt emulated TLS allocator. The linked executable's in-image anchor establishes the load adjustment. Subtracting it from the recorded abort caller and preceding malloc return points to `__emutls_get_address`, specifically the initial per-thread address-array allocation. The completed native call requested 128 bytes and returned null; the disassembly branches directly to abort on that result. This establishes that failure path, not a process-wide RAM limit or a Java heap exhaustion diagnosis.

The JNI packager extracts only `emutls.o` from its temporary SDK libc archive and rewrites its malloc/realloc/free references to the dedicated adapter in `java25/probe/emutls_alloc.*`. The SDK cache and other archive members are unchanged. The adapter uses an aligned size/backend prefix, tries libc first, and then uses page-rounded OS RW mappings. All three allocator references are redirected together so normal releases, array growth and compiler-rt's destructor use matching storage. Failed growth preserves the original data and ownership. Both allocation backends can still fail; compiler-rt retains its existing fatal behavior in that case. There is no heap-size increase or verification bypass.

The adapter and its logger use no compiler TLS or lazy initialization guard. Native key setter return/readback failures receive a separate `EMUTLS: native key update refused` marker, with the actual result and native identity. This diagnostic preserves the native setter's return value and existing SDK semantics. **It does not repair compiler-rt's unchecked native key setter or establish correct storage ownership if that setter fails.** A repeated or refused key update is a separate unresolved runtime issue to act on if this path reaches it on the console; the HotSpot current-pointer fallback is a different key.

The implementation is scoped to embedded JNI probe packages. This does not change independently loaded shared modules' compiler runtimes. The SDK's aligned variable layout, initialization templates, index assignment, thread isolation and native key destructor remain in the original object.

Validation covers the actual adapter header with forced libc and mapping failure under ASan/UBSan, the exact failed 128-byte size, payload alignment, growth/copy and failure preservation, overflow, errno, 1600 concurrent allocation lifetimes and complete release. Target LLVM IR has no emulated TLS or lazy guard. Packaging checks all scoped references and includes the adapter definitions; target console execution is still required.

For the underlying algorithm, see [LLVM compiler-rt emutls.c](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.8/compiler-rt/lib/builtins/emutls.c). The SDK object is adapted in place rather than replaced with that source version.
