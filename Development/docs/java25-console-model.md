# Retail console model query

`java25/platform/console_model.hpp` is an opt-in, allocation-free native helper for consumers. It accepts the SDK `int sceKernelGetHwModelName(char*)` callback, checks zero success, bounds every read, and returns only a model enum/status/native return code. It never queries serial numbers or preserves the raw response. There is no Java runtime, processor-count, scheduler, graphics or default-image change.

The [upstream SDK hwinfo example](https://github.com/ps5-payload-dev/sdk/blob/master/samples/hwinfo/main.c) documents the native signature and uses a 1000-byte buffer and `libkernel_sys`. Our pinned v0.42 SDK includes the same example and export. The native ABI has no size parameter: the helper retains that 1000-byte convention, rejects an unterminated response and parses only within the buffer; it cannot defend against a broken native implementation writing past its own ABI. Null callbacks, native failure, malformed responses and unknown models return unknown. The consumer must supply the real query only on PS5. This is a community SDK API, not a claim of access to Sony's proprietary SDK documentation.

Recognized retail families are CFI-10xx/11xx/12xx/20xx/21xx (standard including Slim) and CFI-70xx/71xx (Pro), with bounded optional A/B and two-digit revision suffixes. [Sony's manual index](https://www.playstation.com/en-us/support/hardware/manuals/) groups those model numbers under PS5 and PS5 Pro respectively. Regional digits do not select a different family. Future revisions, devkits, arbitrary text and non-CFI identifiers stay unknown. Firmware, CPU brand, GPU codename, resolution and user settings are never inputs.

`python3 tools/test_console_model.py` runs the actual header with ASan/UBSan, standard/Pro fixtures, unknown revisions, null/failed query, missing termination and bounded malformed strings. These are host fixtures, not PS5 or Pro detection evidence. Physical queries on both families remain pending. Minecraft-specific formatting/integration belongs in ProsperoCraft, which references this source rather than duplicating it.

## App-safe optional resolution after155 launch failure

ProsperoCraft155 introduced a mandatory libkernel_sys.sprx import absent in153. The user reports immediate launch failure; actual console logs could not yet be retrieved, so loader rejection is a likely cause, not a proven console trace. A payload SDK example is not proof that its system-kernel library is loadable in an application process.

`resolve_loaded_query` now accepts an existing sceKernelDlsym-compatible resolver. It checks loaded-kernel handles1and0x2001, first verifies the kernel's resolver export, and accepts the model-query address only on zero success with nonnull output. These handles follow the [SDK's rtld process-type selection](https://github.com/ps5-payload-dev/sdk/blob/master/crt/rtld_sprx.c). It never loads a module or introduces a direct model-query import. Missing export/error/null callback yields unavailable/unknown. The consumer must initialize logging first. Native invocation and model output remain physically unvalidated; absence of a query must never prevent ordinary startup. Tests cover both handle fixtures, lookup failure with poisoned nonnull output and missing export.
